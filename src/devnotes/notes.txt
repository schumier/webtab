Exactly — you should not send every UIM to Hive investigation. The combination of Trend + Historical Pattern should help determine which UIMs actually deserve investigation.

I would start with a simple investigation matrix:

Trend	Historical Pattern	Suggested Action	Why

🔴 Deteriorating	New	🔴 Investigate	New adverse movement
🔴 Deteriorating	Persistent	🔴 Investigate / Review	Existing issue continues to worsen
🔴 Deteriorating	Recurring	🔴 Investigate	Previous issue has returned and is worsening
🟢 Improving	Persistent	🟡 Monitor / Review	Still abnormal, but moving in right direction
🟢 Improving	Recurring	🟡 Monitor	Currently improving; previous history available
→ Stable	Persistent	🟡 Monitor	Issue remains but isn't getting worse
→ Stable	Recurring	🟡 Monitor / Review previous observation	May already have an explanation
🟢 Improving	Resolved	🟢 No investigation	Returned toward normal
→ Stable	Resolved	🟢 No investigation	No current concern


But I would add one more condition: severity

This is important. Deteriorating doesn't automatically mean investigate.

For example:

100 → 101 → 102 → 103

Technically deteriorating, but probably not worth going into Hive.

Whereas:

100 → 105 → 110 → 180

is different.

So your investigation decision should be more like:

> Trend + Historical Pattern + Magnitude/Statistical Deviation



For example:

Investigate

Deteriorating + New + outside statistical tolerance

Deteriorating + Recurring + outside tolerance

Deteriorating + Persistent + materially worse

Any extremely unusual statistical movement, regardless of pattern


Monitor

Persistent but Stable

Persistent but Improving

Small deterioration still within normal historical variability

Recurring but currently within expected range


No Action

Resolved

Stable within normal range

Improving and back within normal range


Previous Hive observations can reduce unnecessary investigation even further

This is where the observation history you mentioned becomes really valuable.

Suppose:

> UIM A
Trend: Deteriorating
Pattern: Recurring
Statistical deviation: High
Previous Hive observation: “Expected seasonal increase at quarter end.”



Instead of immediately reinvestigating, the dashboard could show:

⚠ Review Previous Observation

The analyst checks whether the same explanation applies before running another Hive investigation.

Compare that with:

> UIM B
Trend: Deteriorating
Pattern: New
Statistical deviation: High
Previous observation: None



That should probably go straight to:

🔴 Hive Investigation

This gives you a useful fourth output

Rather than just Trend and Pattern, derive:

Recommended Review Action

🔴 Hive Investigation
🟠 Review Previous Observation
🟡 Monitor
🟢 No Action

For your ~1,000 UIM population, that's probably one of the most useful summary metrics:

> ~1,000 UIMs analyzed
14 Hive Investigation
11 Review Previous Observation
32 Monitor
Remaining: No Action



Then analysts don't have to interpret hundreds of combinations themselves.

And importantly, I would call this “Recommended Review Action”, not automatically say “Issue” or “Root Cause.” The dashboard is prioritizing where human investigation is worthwhile; Hive and the analyst still determine what actually happened.

I would actually use four final statuses

This is simple enough for users:

🔴 Investigate
New/unexplained/materially abnormal movement requiring Hive.

🟠 Review Previous Observation
Similar historical movement exists; analyst checks whether the previous explanation still applies.

🟡 Monitor
Still showing an exception/pattern but stable or improving and doesn't currently justify Hive work.

🟢 No Action
Within normal range, resolved, or previously validated expected behaviour remains applicable.

This gives you a very useful summary at the top of the page:

> August Month-End — 980 UIMs analyzed
🔴 12 Investigate | 🟠 8 Review Previous Observation | 🟡 24 Monitor | 🟢 936 No Action



One thing I wouldn't fully automate

I wouldn't let Python read a free-text Hive remark and automatically decide that something is normal. In a banking environment, that's difficult to explain and potentially risky.

Instead, when the analyst enters the observation, have them explicitly select:

Outcome = Expected/Normal

and perhaps:

Reusable for similar future movement = Yes

Then your decision logic is deterministic and auditable.

So the full concept becomes:

> Statistics identify unusual behaviour → history identifies whether it is new/persistent/recurring → previous validated observations prevent unnecessary repeat investigation → analysts investigate only the remaining unexplained material movements.



That, to me, is the strongest version of the analysis feature you've been developing.






Yes. I would make Observation Outcome describe what the analyst concluded from Hive, while Future Occurrence = Yes/No means whether this conclusion can be reused when a similar pattern appears again.

Observation Outcome	Example scenario after Hive investigation	Future Occurrence

Expected / Normal	UIM increases every quarter-end because business volume normally rises. No data problem found.	Yes if this behaviour is expected to repeat under the same circumstances
Expected / Normal	One-time portfolio migration caused the increase, but data is correct.	No because it was a one-off event
Known Issue	Upstream team has an existing defect/ticket causing duplicates and it remains unresolved.	Yes while the known issue remains active
Known Issue	Known defect caused this month-end issue but has now been fixed.	No because future occurrences shouldn't automatically be attributed to the fixed issue
Data Issue	Hive confirms unexpected duplicate records caused by incorrect source data. New issue, remediation required.	Usually No initially
Data Issue	A known recurring source-data behaviour is confirmed and expected to continue until a planned remediation.	Could be Yes, although I would normally classify this as Known Issue after the first investigation
Under Investigation	Hive analysis started but root cause isn't established yet / waiting for upstream team confirmation.	No — never automatically reuse an unresolved conclusion
Other	Explanation doesn't fit the categories, e.g. exceptional regulatory exercise or special business event.	Yes/No depending on whether it can reasonably recur


There is one terminology change I'd recommend, though.

Don't call it simply “Future Occurrence”

That could be interpreted as:

> “Do you think this issue will happen again?”



That's not quite what you need.

What you actually want to know is:

> “If a similar movement occurs again, can this observation be used to explain it?”



So I'd name the field:

Reusable for Similar Occurrence? — Yes / No

For example:

> Outcome: Expected / Normal
Observation: Higher facility population is expected at quarter-end.
Reusable for Similar Occurrence: Yes



Next quarter:

Same UIM + similar magnitude + same period/pattern

→ dashboard finds the previous observation
→ 🟠 Review Previous Observation
→ analyst confirms it still applies
→ 🟢 No Further Investigation

I wouldn't automatically make reusable = No mean Hive investigation either

Consider:

> Outcome = Expected / Normal
Reusable = No
Reason = One-time migration in August.



If September is normal, nothing needs investigation.

If September has another abnormal movement, then the August explanation cannot be reused, so that new unexplained movement may require Hive investigation.

Known Issue needs one additional concept

For Known Issue, I'd strongly consider storing an Issue Status or reference:

> Known Issue: Upstream duplicate-generation defect
Reference: INC/Problem ID if available
Status: Open
Reusable: Yes



Then next month if the same UIM deteriorates:

Known issue still Open + similar behaviour

→ 🟠 Review Known Issue / Monitor

rather than immediately repeating the same Hive investigation.

But if:

Known issue = Closed

and the same abnormality comes back:

→ 🔴 Investigate

because you shouldn't automatically assume a closed issue caused it again.

So your observation form could be very simple

Month-End: 31-Aug-2026
Observation Date: 03-Sep-2026
Outcome: Expected / Normal ▼
Observation: Increase due to expected quarter-end facility volume.
Reusable for Similar Occurrence?: Yes
Status/Reference: optional, mainly for Known Issue

That gives Python structured information for future decision-making while keeping the actual Hive conclusion as human-entered evidence.
